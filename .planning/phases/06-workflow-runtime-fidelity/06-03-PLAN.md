# Plan 06-03: Bridge $GSD_SDK to Pi Runtime

## Problem

`--chain` and `--auto` workflows contain **424 occurrences** of `$GSD_SDK query` across **91 unique sub-commands**. The `$GSD_SDK` CLI binary ships with the upstream package and works in Claude Code, but Pi has no `bash` tool and no `$GSD_SDK` on PATH.

The upstream SDK is a Node.js library (`@opengsd/get-shit-done-redux/sdk/dist/query/`) with **65 importable handler modules** exposing async functions like `configGet()`, `initPhaseOp()`, `checkAutoMode()`, `stateGet()`, etc. These are already a direct `require()` away from our extension code.

## Approach: SDK API Bridge + Pi Tool Registration

### Architecture

```
$GSD_SDK query config-get workflow.auto_advance
                    ↓ (generation-time text replacement)
Use the gsd_query tool: gsd_query({command: "config-get", args: ["workflow.auto_advance"]})
                    ↓ (runtime)
Pi extension routes to: configGet(["workflow.auto_advance"], projectDir)
                    ↓
Returns: { data: false }
```

**One Pi tool (`gsd_query`) + one routing layer = all 91 sub-commands.**

### Why this beats "natural language replacement"

| Aspect | Natural language | SDK bridge |
|---|---|---|
| Precision | "Check if auto mode is active" → LLM interprets | `gsd_query({command: "check-auto-mode"})` → deterministic JSON |
| Reliability | Depends on LLM comprehension | Deterministic function call |
| Testability | Hard to test fuzzy instructions | Unit test each handler |
| Upstream compatibility | Breaks when upstream changes | SDK API is stable; route map is small |
| Coverage | Only top N patterns | All 91 sub-commands |
| Effort | Per-pattern manual replacement | One routing layer + one tool |

### What we build

**1. Pi tool: `gsd_query`**

```typescript
// src/gsd-query-tool.ts
{
  name: "gsd_query",
  description: "Query GSD project state, config, and phase information",
  parameters: {
    command: { type: "string", description: "Query command (e.g. 'config-get', 'state.load', 'init.phase-op')" },
    args: { type: "array", items: { type: "string" }, description: "Command arguments" },
    pick: { type: "string", description: "Extract a specific field from JSON result" },
    projectDir: { type: "string", description: "Project root directory (defaults to cwd)" }
  }
}
```

Routing layer maps `command` to the correct SDK handler function. Supports `--pick` for field extraction (mirrors `$GSD_SDK query ... --pick <field>`).

**2. Generation-time transform: `transformGsdSdkCommands(input: string): string`**

Replaces `$GSD_SDK query <subcommand> <args...>` in both regular text and bash code blocks with:

```
Use the gsd_query tool: gsd_query({command: "<subcommand>", args: ["<arg1>", "<arg2>"]})
```

For `--pick` variants:
```
Use the gsd_query tool: gsd_query({command: "<subcommand>", args: ["<arg1>"], pick: "<field>"})
```

For mutation commands (`config-set`, `commit`, `state.update`, etc.), replaces with:
```
Use the gsd_query tool: gsd_query({command: "<subcommand>", args: ["<key>", "<value>"]})
```

**3. Variable interpolation mapping**

| $GSD_SDK variable | Pi equivalent |
|---|---|
| `${PHASE}` | Referenced from `$ARGUMENTS` or `init.phase-op` result |
| `${PHASE_NUM}` | Referenced from `$ARGUMENTS` |
| `${GSD_WS}` | Referenced from `$ARGUMENTS --ws` |
| `${PADDED_PHASE}` | Computed from `init.phase-op` result |

## Steps

### Step 1: Create `gsd_query` tool with routing layer (TDD red)

- Create `src/gsd-query-tool.ts` with:
  - Pi tool definition (`name`, `description`, `inputSchema`)
  - `execute()` handler that routes `command` to the correct SDK handler
  - `--pick` support for field extraction
  - Error handling for unknown commands
- Create `tests/gsd-query-tool.test.ts` with tests for:
  - Each P0 command (15+ tests)
  - `--pick` field extraction
  - Unknown command error
  - Project directory resolution

### Step 2: Create `transformGsdSdkCommands()` (TDD green)

- Implement in `src/prompt-transform.ts`
- Two replacement patterns:
  1. `$(GSD_SDK query <subcmd> <args...>)` bash capture form → `gsd_query({command: "<subcmd>", args: [...]})`
  2. `$GSD_SDK query <subcmd> <args...>` plain form → same gsd_query call
- Handle `--pick <field>` flag
- Handle `2>/dev/null || echo "default"` fallback patterns
- Handle `$( )` subshell capture wrapping
- Idempotent: no double-transformation

### Step 3: Wire into pipeline

- Add `transformGsdSdkCommands` to `applyPromptTransforms()` after `transformSubagentDispatchForPi`
- Add to `transformWorkflowCodeFences()` for code-fenced bash blocks
- Register `gsd_query` tool in extension manifest

### Step 4: Integration tests

- Assert zero `$GSD_SDK` in `generated/prompts/` and `generated/workflows/`
- Assert `gsd_query` calls appear in transformed output
- Assert `gsd_query` tool is registered and functional
- Test P0 commands return correct data against this project's `.planning/` directory
